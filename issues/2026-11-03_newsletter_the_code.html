Why Proton’s AI push sparked a backlash, and what devs can learn from it

Source: X.com

Speed at what cost. Proton, the Swiss company behind Proton Mail, is going all in on AI and things are getting messy. A 404 Media investigation published last week revealed that CEO Andy Yen dismissed an engineer’s request to pentest new code as “loser thinking.” And that was just the beginning. He also told staff that 2026 would be the last year Proton hires engineers and announced AI re-interviews that could decide who keeps their job. Unsurprisingly, that didn’t go down well.

A quick U-turn. Users started canceling subscriptions and calling for Yen’s resignation. A day later, he scrapped the re-interviews, admitted a communication failure on his part, and Proton apologized publicly. But the AI push isn’t going anywhere. Employees say the re-interview criteria are being folded into performance reviews.

The real takeaway. CTO Bart Butler’s leaked manifesto is worth your attention. Here are the ideas you can put to work:

  • Direct the code, don’t type it. Butler compares writing code by hand to memorizing phone numbers. Programming is dead, he writes, but engineering and expertise are not.

  • Manage agents like direct reports. When one fails, update your repo context files, shared prompts, and skills so the team never hits that failure again.

  • Keep your judgment in the loop. Models hallucinate and get misled by malicious inputs. Your experience catches what they miss.

  • Hunt down the next bottleneck. Faster coding just moves the slowdown. Look at your CI, specs, approvals, and code review, and redesign them around AI.

Two sides to it. Reactions have been mixed. Ruby on Rails creator DHH defended the push, while Clean Code author Robert “Uncle Bob” Martin echoed the manifesto’s core argument. Critics, meanwhile, focused on Proton’s workplace culture. Either way, if you’re an engineer in 2026, there’s plenty worth borrowing from Butler’s full manifesto.

AI CODING HACK

How to get real performance fixes from Claude Code

Tell Claude Code to “make it faster” and it usually adds a cache. A dev shared a perf-review prompt that names the exact structures to ask for instead.

  • Step 1: Save it as a reusable slash command. Create a file at “claude/commands/perf-review.md” and paste the full prompt. The short version:
Do a performance review of this project:
1. Profile first. Find the 5 slowest spots.
2. Match each spot to one case only:
- Uses a cache → redesign, don't add more caches
- Hot loop hitting hash tables → flat array + indices
- Many objects, few fields read → struct of arrays (SoA)
- Serial awaits → run in parallel
- No match → data-oriented rewrite
3. Report current time, matched case, file + lines,
expected speedup. Don't change anything yet.
  • Step 2: Run “/perf-review” in any project. Claude profiles first, matches each hotspot against the cases, and reports before touching code.

Expect a report with files, lines, and estimated speedups. Approve the changes you want, skip the rest.
